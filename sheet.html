1.1 ทำไมสร้างระบบ และต้องศึกษาอะไรก่อน objectives, feasibility

ศัพท์ความหมาย
วัตถุประสงค์สร้าง/ปรับปรุงระบบ 5 ข้อImprove Service ปรับปรุงบริการลูกค้า/ผู้ใช้ให้ดีขึ้น; Support for new products and services รองรับบริการใหม่; Better performance ทำงานมีประสิทธิภาพขึ้น; Stronger control ควบคุมได้ดีขึ้น; Reduced cost ลดต้นทุน
ความเป็นไปได้ 3 ด้าน Feasibilityต้องศึกษาก่อนลงมือสร้างระบบ
Technical feasibilityเทคนิค: เทคโนโลยี ฮาร์ดแวร์ ทักษะทีมที่มี สร้างระบบนี้ได้จริงไหม
Economic feasibilityเศรษฐศาสตร์: ผลตอบแทนคุ้มกับต้นทุนไหม (คำนวณด้วย Payback / NPV ในบทที่ 3)
Schedule feasibilityเวลา: ทำเสร็จทันกำหนดไหม (ใช้ตารางเวลา Gantt / PERT)

หลังศึกษาความเป็นไปได้แล้ว ผู้พัฒนาต้องทำต่อ 5 อย่าง: กำหนดขอบเขตงาน project scope; กำหนดวัตถุประสงค์หลัก project goal; ระบุปัญหาของระบบปัจจุบัน problem identification; ประมาณต้นทุน cost estimation; ระบุทรัพยากรที่ต้องใช้ identify required resources.

1.4 คำนวณ: เส้นทางวิกฤตและ Slack critical path, slack

ใช้เมื่อ โจทย์ให้ตารางงาน (ระยะเวลา + งานก่อนหน้า) แล้วถามเวลาโครงการต่ำสุด เส้นทางวิกฤต หรือ slack ของงาน.

วิธีที่ 1: ไล่ทุกเส้นทาง (เร็ว เหมาะข้อสอบ)

  1. วาด PERT: งานที่ไม่มีงานก่อนหน้า (-) เป็นจุดเริ่ม; ลูกศรจากงานก่อนหน้าไปงานที่ตามมา
  2. ไล่ทุกเส้นทางจากจุดเริ่มถึงจุดสุดท้าย บวกระยะเวลา เช่น A+B+D
  3. เส้นทางที่ ยาวที่สุด = critical path; เวลานั้น = เวลาโครงการต่ำสุด (ใส่ * ที่เส้นวิกฤต)
  4. งานบนเส้นวิกฤต slack = 0; งานอื่น slack = (ความยาวเส้นวิกฤต) − (ความยาวเส้นที่ยาวที่สุดที่งานนั้นอยู่)

วิธีที่ 2: Forward / Backward pass (ใช้เมื่อถาม ES EF LS LF)

EF = ES + D  ES = max EF ของงานก่อนหน้า
LS = LF − D  LF = min LS ของงานที่ตามมา
Slack = LS − ES = LF − EF
สัญลักษณ์ความหมายหาจากไหน
DDuration ระยะเวลางานจากตารางโจทย์
ESEarliest Start เริ่มเร็วสุดงานแรก = 0; งานอื่น = EF ที่มากสุดของงานก่อนหน้า (รอตัวช้าสุด)
EFEarliest Finish เสร็จเร็วสุดES + D (forward pass: ไล่ซ้ายไปขวา)
LFLatest Finish เสร็จช้าสุดที่ยังไม่ทำให้โครงการช้างานสุดท้าย = EF ของมัน (= เวลาโครงการ); งานอื่น = LS ที่น้อยสุดของงานที่ตามมา
LSLatest Start เริ่มช้าสุดLF − D (backward pass: ไล่ขวาไปซ้าย)
Slackเวลาหย่อนLS − ES; = 0 แปลว่างานอยู่บนเส้นวิกฤต

1.5 คำนวณ: Crash (อัดฉีดเงินลดเวลา) แบบ CPM crash cost per day, crash table

ใช้เมื่อ โจทย์ให้ Normal time/cost และ Crash time/cost แล้วถามว่าลดเวลาโครงการได้กี่วัน ใช้เงินเท่าไร.

ลดได้สูงสุดm = Tn − Tc

สัญลักษณ์ความหมายหาจากไหน
TnNormal duration เวลาปกติคอลัมน์ Normal Duration
TcCrash duration เวลาเมื่ออัดฉีดเต็มที่คอลัมน์ Crash Duration

Totalต้นทุนรวมโครงการเริ่มต้น = ผลบวก Normal cost ของ ทุกงาน (รวมงานนอกเส้นวิกฤต) แล้วบวกเงินอัดฉีดทีละขั้น

ขั้นตอน

  1. คำนวณ m และ k ของทุกงาน (ตาราง); ต้นทุนเริ่มต้น = ผลรวม Normal cost
  2. ไล่ทุกเส้นทางและเวลารวม; ใส่ * ที่เส้นที่ยาวที่สุด (ถ้ายาวเท่ากันหลายเส้นก็ * ทุกเส้น)
  3. เลือกงานที่จะ crash: ต้อง อยู่บนเส้นวิกฤต ยังเหลือ m และ ลดแล้วทุกเส้นวิกฤตสั้นลงพร้อมกัน; ถ้ามีหลายเส้นวิกฤต ให้เลือกงานร่วม (อยู่ในทุกเส้น) ที่ k ต่ำสุด หรือจับคู่หลายงาน (เช่น B+C) ให้ครอบคลุมทุกเส้น
  4. ลดกี่วัน = ค่าน้อยกว่าระหว่าง (m ที่เหลือ) กับ (ช่องว่างระหว่างเส้นวิกฤตกับเส้นที่ยาวรองลงมา) ไม่งั้นเส้นวิกฤตเปลี่ยนกลางทาง (สไลด์: E ลดได้ 3 แต่ลดแค่ 1 เพราะ ACD = 19 รออยู่)
  5. อัปเดตตาราง: ลบวันออกจากทุกเส้นที่มีงานนั้น; ต้นทุนรวม += วัน × k; ทำเครื่องหมาย * ใหม่
  6. หยุดเมื่อ งบเต็ม / ไม่มีงานให้ crash ต่อ (m หมด) / ถึงเป้าเวลาที่โจทย์กำหนด; ตอบเวลาใหม่ ต้นทุนรวม และส่วนต่างจากเดิม

3NFเป็น 2NF และ ไม่มี non-key ขึ้นกับ non-key อื่น (ไม่มี transitive dependency)แยก field ที่ขึ้นกับ non-key ออกเป็นตารางใหม่ มี non-key ตัวนั้นเป็น PK (และคงไว้ในตารางเดิมเป็น FK)field นี้ขึ้นกับ field ธรรมดาอื่นหรือไม่

จำ 3NF: ทุก field ขึ้นกับ the key, the whole key, and nothing but the key. ตาราง 1NF ที่ PK เป็น field เดียว = 2NF อัตโนมัติ (ไม่มี "บางส่วน" ของ key). ถ้า PK ไม่ใช่ combination key ข้ามขั้น 2NF ได้.

3.7 คำนวณ: NPV (Net Present Value) decision rules

ใช้เมื่อ ถามว่าควรลงทุนในระบบนี้หรือไม่ / เลือกโครงการไหน, หรือถามมูลค่าสุทธิเป็นเงิน.

NPV = PV(รับ) − PV(จ่าย) = Σt=0T (Bt − Ct)(1 + r)t
สัญลักษณ์ความหมายหาจากไหน
Btประโยชน์ (กระแสเงินสดรับ) ปีที่ tตารางรายได้ของโจทย์
Ctต้นทุน (กระแสเงินสดจ่าย) ปีที่ tเงินลงทุนปี 0 และต้นทุนปีอื่น (ถ้ามี)
rอัตราคิดลดโจทย์ให้
t, Tt = 0 คือปีปัจจุบัน, T = ปีสุดท้ายของโครงการนับจากตารางโจทย์
  1. คิด PV ของรายรับทุกปี (รายได้ × PV factor)
  2. คิด PV ของรายจ่ายทุกปี (เงินลงทุนปี 0 ไม่ต้องลด)
  3. NPV = รวม PV รับ − รวม PV จ่าย
  4. ตัดสินใจตามกฎด้านล่าง เขียนเหตุผลเป็นประโยค
ผลความหมายตัดสินใจ
NPV > 0ลงทุนแล้วมีกำไร มูลค่ากิจการเพิ่มขึ้นลงทุน
NPV = 0ผลตอบแทนเท่ากับต้นทุนเงินทุนพอดีเกณฑ์ NPV ≥ 0 ยอมรับได้ (ไม่ขาดทุนเชิงมูลค่า)
NPV < 0ผลตอบแทนต่ำกว่าต้นทุนเงินทุนไม่ลงทุน
โครงการ ทดแทนกันได้ (mutually exclusive)เลือกได้อย่างเดียวเลือกตัวที่ NPV สูงกว่า
โครงการ อิสระต่อกัน (independent)ลงทุนได้ทุกโครงการลงทุนทุกโครงการที่ NPV เป็นบวก (เช่น ทั้งโครงการ S และ L)

Data validation checks 8 แบบ

Checkตรวจอะไรตัวอย่างที่ใช้ตอบ
1 Sequence checkลำดับ/ความต่อเนื่องของข้อมูลเลขที่ใบสั่งซื้อต้องเรียงต่อเนื่อง ไม่ขาด/ซ้ำ
2 Existence checkฟิลด์ที่บังคับกรอก มีข้อมูลหรือไม่ (ไม่ว่าง)ต้องกรอกชื่อลูกค้า
3 Data type checkชนิดข้อมูลถูกต้องจำนวนเงินต้องเป็นตัวเลข ไม่มีตัวอักษร
4 Range check (limit check)ความยาวหรือช่วงของค่าอยู่ในขอบเขตตายตัวเดือน 1 ถึง 12; คะแนน 0 ถึง 100
5 Reasonableness checkค่า สมเหตุสมผล ตามบริบท แม้ยังอยู่ในช่วงชั่วโมงทำงาน 24 ชั่วโมงต่อวันทุกวัน; ซื้อ 10,000 ชิ้นจากลูกค้ารายย่อย
6 Validity check (referential integrity)ค่ามีอยู่จริงในตาราง/รายการที่อนุญาตรหัสลูกค้าต้องมีใน CUSTOMER; รหัสสินค้าต้องอยู่ใน PRODUCT
7 Combination checkใช้ 2 ฟิลด์ขึ้นไปร่วมกัน ตรวจรหัสไปรษณีย์ต้องตรงกับจังหวัด; ประเภทสินค้ากับจำนวนที่ขายได้
8 Batch controls (hash totals)จำนวนข้อมูลทั้งหมดของชุด/ผลรวมควบคุม ต้องตรงกับยอดที่ตั้งไว้นับใบสั่งซื้อในชุดได้ 50 ใบ ต้องตรงยอดควบคุม 50; hash total = ผลรวมรหัสที่ไม่มีความหมายทางบัญชี
Input controlทุกฟิลด์ต้องตรวจสอบได้: Audit trail บอกที่มาของข้อมูล (ใคร key เมื่อไหร่ จากกระบวนการไหน); Data security ป้องกันความเสียหายต่อข้อมูล; Encryption ข้อมูลบางอย่างต้องเข้ารหัส

  2. ถ้า export เป็นรูปแบบที่ระบบใหม่รู้จักไม่ได้ ต้อง เขียนโปรแกรมแปลง อ่านข้อมูลเก่าเข้าไปไว้ในระบบใหม่
  3. ต้องมีวิธี ตรวจสอบ ว่าข้อมูลในระบบใหม่ถูกต้องหรือไม่

5.7 การบำรุงรักษา (Maintenance) 4 ประเภท corrective, adaptive, perfective, preventive

ประเภทตามสไลด์สัญญาณในโจทย์ข้อควรรู้
Corrective แก้ไขวินิจฉัยและ แก้ข้อผิดพลาด ของระบบที่ใช้งานอยู่ระบบพัง บั๊ก ข้อมูลผิดตอบสนองตามลักษณะของ error; เลวสุด = ระบบล่ม; กลับมาใช้ได้แล้วต้องหาสาเหตุ วิเคราะห์ และออกแบบ วิธีแก้ถาวร
Adaptive ปรับเพิ่มเพิ่มความสามารถ (enhancements) ให้ระบบ และทำให้ใช้ง่ายขึ้นเพิ่มฟีเจอร์/รายงาน ปรับให้ใช้ง่ายยากกว่าพัฒนาระบบใหม่ เพราะต้องทำภายใต้ข้อจำกัดของระบบเดิม
Perfective ปรับปรุงให้ดีขึ้นเปลี่ยนระบบให้ มีประสิทธิภาพ เชื่อถือได้ และดูแลรักษาง่ายขึ้นทำให้เร็วขึ้น เสถียรขึ้น ปรับโครงสร้างโค้ดคุ้มค่าที่สุดช่วง กลางอายุ ระบบ; โปรแกรมที่ต้องแก้มาก = ตัวเลือก reengineering; ยิ่งแก้มากยิ่งไม่มีประสิทธิภาพและดูแลยาก
Preventive ป้องกันวิเคราะห์จุดที่มีโอกาสเกิดปัญหา เพื่อป้องกันก่อนเกิดตรวจสอบเชิงรุก ป้องกันล่มฝ่าย IT มักเป็นผู้เริ่ม; ผลคือผู้ใช้พอใจขึ้น downtime ลด และ TCO ลด; บางครั้งไม่ได้รับความสำคัญเท่าที่ควร

ใช้นิยามตามสไลด์ (Adaptive = เพิ่ม enhancement; Perfective = ประสิทธิภาพ/เชื่อถือได้/ดูแลง่าย). ตำราบางเล่มให้ adaptive = ปรับตามสภาพแวดล้อมที่เปลี่ยน ถ้าสับสนให้เขียนนิยามตามสไลด์กำกับ.
