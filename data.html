ออกแบบฐานข้อมูล

ข้อสอบให้ตารางเดียวที่ยัดทุกอย่างไว้ด้วยกัน แล้วสั่งให้ [[norm|normalize]] ถึง 3NF โดยระบุ [[pk]], [[fk]] และ [[fd|dependency]] ของทุกขั้น จากนั้นวาด [[erd]] พร้อม [[cardinality]] ท้ายบทมีแม่แบบคำตอบที่เขียนตามได้ทีละขั้น

เก็บข้อมูลที่เดียว ใช้ร่วมกันทุกระบบFile processing vs Database

ระบบแบบ [[filesys]] ให้แต่ละระบบมีไฟล์ของตัวเอง ข้อมูลเดียวกันจึงถูกเก็บซ้ำหลายที่ ([[redundancy]]) ส่วน [[database]] เก็บครั้งเดียวแล้วให้ทุกระบบใช้ร่วมกัน

ร้านของ Mario ใช้สองระบบแยกกัน ร้านของ Danica ใช้ฐานข้อมูลเดียว (สไลด์ 3) ลองเปลี่ยนเบอร์โทรลูกค้าในทั้งสองแบบ

file processing ยังมีที่ใช้ เมื่อต้องประมวลผลข้อมูลโครงสร้างตายตัวปริมาณมากเป็นประจำ เช่น บริษัทบัตรเครดิตที่ลงรายการวันละหลายพันรายการ ในกรณีนั้นคุ้มค่ากว่า ข้อดีของ database ที่สไลด์สรุปไว้มี 6 ข้อ:

  • [[scal]]: ขยาย แก้ไข หรือลดขนาดระบบได้
  • [[econ]]: ใช้ฮาร์ดแวร์ได้คุ้มขึ้น
  • ระดับองค์กร: มี [[dba]] ประเมินความต้องการภาพรวมและดูแลฐานข้อมูล
  • [[stdz]]: ชื่อ รูปแบบ เอกสารเหมือนกันทั้งองค์กร
  • [[secur]]: เฉพาะผู้มีสิทธิ์ และแต่ละคนได้ระดับต่างกัน
  • [[indep]]: ระบบไม่ผูกกับวิธีเก็บข้อมูลจริง

DBMS ประกอบด้วยอะไรDBMS components

[[dbms]] คือระบบที่ช่วยจัดการข้อมูลในฐานข้อมูล (เพิ่ม แก้ ลบ) เช่น Access, Oracle, MySQL มี 4 ส่วนที่ต้องจำ: [[iface|interface]] ของผู้ใช้ DBA และระบบอื่น, [[dml]], [[schema]] กับ [[subschema]], และ [[repo|physical data repository]]

เลือกว่าใครเป็นคนส่งคำสั่ง แล้วเลื่อนดูเส้นทางของคำสั่งหนึ่งคำสั่งผ่านแต่ละส่วน กล่อง schema คือทุกตารางในฐานข้อมูล ส่วนที่สว่างขึ้นคือ subschema ของคนนั้น

เมื่อต่อฐานข้อมูลเข้ากับเว็บ ต้องมี [[middleware]] คั่นกลาง เพราะฐานข้อมูลใช้ภาษาและคำสั่งที่ไม่เกี่ยวกับ HTML เลย ข้อมูลบนเว็บต้องปลอดภัย แต่ผู้มีสิทธิ์ก็ต้องเข้าถึงได้ง่าย

ศัพท์ตาราง: entity, field, recordData design terms

[[entity]] คือสิ่งที่เราเก็บข้อมูล (คน สถานที่ สิ่งของ เหตุการณ์) แต่ละ entity ได้ [[table]] หนึ่งตาราง คอลัมน์คือ [[field]] แถวคือ [[record]] และ field ที่โผล่ในหลายตารางเรียก [[commonfield]]

เลือกศัพท์แล้วดูว่ามันชี้ที่ส่วนไหนของตาราง หรือแตะส่วนของตารางเอง

Key: field ที่ระบุแถวPrimary, combination, candidate, foreign, secondary

[[pk]] คือ field (หรือหลาย field รวมกัน) ที่ระบุแถวได้เจาะจงเพียงแถวเดียวและไม่เกินจำเป็น ถ้าต้องใช้หลาย field เรียก [[combkey]] ตัวเลือกอื่นที่เป็น PK ได้เรียก [[candkey]] field ที่ชี้ไป PK ของอีกตารางคือ [[fk]] และ field ที่ใช้ค้นหาโดยไม่ต้อง unique คือ [[seckey]]

แตะหัวคอลัมน์ของตาราง STUDENT เพื่อเลือก field (เลือกได้หลายตัว) ระบบจะตรวจว่ากลุ่มที่เลือกระบุแถวได้เจาะจงและไม่เกินจำเป็นไหม

Referential integrity: FK ต้องชี้ถึงของจริงReferential integrity

[[ri]] คือชุดกฎกันข้อมูลขัดแย้ง ใจความคือค่า FK ต้องตรงกับ PK ที่มีอยู่จริงเสมอ จึงเพิ่มลูกที่ไม่มีแม่ไม่ได้ และลบแม่ที่ยังมีลูกไม่ได้

CUSTOMER ถือ PK (แม่) ORDER ถือ FK (ลูก) ลองสั่งทั้งสี่แบบ ทั้งตอนเปิดและปิดกฎ แล้วดูว่าตารางเสียหายแบบไหน

ความสัมพันธ์ 1:1, 1:M, M:NEntity-Relationship Diagram

ใน [[erd]] entity เป็นกล่องที่ตั้งชื่อด้วยคำนามเอกพจน์ ความสัมพันธ์เป็นเส้นที่ตั้งชื่อด้วยคำกริยา มี 3 แบบ: [[r11]], [[r1m]] และ [[rmn]] ซึ่งเก็บตรงๆ ไม่ได้ ต้องคั่นด้วย [[assoc]]

วงกลมซ้ายและขวาคือ record ของแต่ละ entity เส้นคือการจับคู่ ลองสลับแบบ แล้วกดแก้ M:N ด้วย associative entity

ใน 1:M ตารางฝั่ง many ถือ FK ไปหาฝั่ง 1 ส่วน associative entity ถือ FK สองตัว ไปหา entity ทั้งสองฝั่ง และ PK ของมันคือ FK สองตัวนั้นรวมกัน ตั้งชื่อตามเหตุการณ์ที่จับคู่ เช่น GRADE, ORDER LINE

Cardinality และสัญลักษณ์ตีนกาCrow's foot notation

[[cardinality]] บอกว่า record ของ entity หนึ่งเกี่ยวกับ record ของอีก entity ได้กี่ตัว ใช้ [[crow|crow's foot]] ที่ปลายเส้น: [[sbar|ขีด]] = หนึ่ง, [[scircle|วงกลม]] = ศูนย์, [[sfoot|ตีนกา]] = หลาย และสัญลักษณ์ที่ติดกล่องไหน บอกจำนวนของกล่องนั้น

สัญลักษณ์ที่ติดกล่อง ORDER บอกว่าลูกค้าหนึ่งคนมี ORDER ได้กี่ใบ ไม่ใช่ ORDER หนึ่งใบมีลูกค้ากี่คน แตะแต่ละปลายเส้นเพื่ออ่านทีละทิศ และปรับขั้นต่ำ ขั้นสูงเองได้

ทำไมต้อง normalizeNormalization and anomalies

[[norm]] คือการจัดให้ข้อมูลแต่ละเรื่องอยู่ในตารางของมันเองที่เดียว เพื่อไม่ให้เกิด [[anomaly]] ตอนเพิ่ม แก้ ลบ ข้อมูล หลักออกแบบของอาจารย์ (สไลด์ 41):

  1. เน้นลดความซ้ำซ้อนของข้อมูลเป็นหลัก
  2. ออกแบบให้เพิ่มหรือแก้ข้อมูล (Insert, Update) ได้ง่ายและไม่ผิดพลาด
  3. เก็บข้อมูลเป็นหลายตารางที่สัมพันธ์กัน
  4. เก็บค่าเฉพาะเท่าที่จำเป็น
  5. ไม่เก็บค่าที่มาจากการคำนวณ เช่น ยอดรวมต่อบรรทัด = จำนวน × ราคา ให้คำนวณตอนแสดงผล
  6. ทุกตารางต้องมี [[pk|Primary key]]
  7. ตารางเชื่อมกันด้วย [[fk|Foreign key]]

ลองแก้ข้อมูลในตารางนัดหมายแบบตารางเดียว แล้วสลับไปดูหลังแยกตาราง

ประโยชน์ของ normalization ที่สไลด์ 43 สรุป: ลดที่ว่างที่ใช้เก็บข้อมูล, ลดความผิดพลาดที่ข้อมูลไม่ตรงกัน, ลด anomaly ของการลบและแก้ไข, และเพิ่มความคงทนให้โครงสร้างฐานข้อมูล

คำถามเดียวที่ตัดสิน 2NF และ 3NFFunctional dependency

[[fd|Functional dependency]] B → A แปลว่ารู้ค่า B แล้วบอกค่า A ได้แน่นอน ตารางจะผ่าน 3NF เมื่อทุก field ขึ้นกับ key, ทั้ง key และไม่ขึ้นกับอะไรนอกจาก key: [[nf2|2NF]] ห้ามขึ้นกับ key แค่บางส่วน ([[partial]]) [[nf3|3NF]] ห้ามขึ้นกับ field ที่ไม่ใช่ key ตัวอื่น ([[transitive]])

สองตัวอย่างนี้คือตัวอย่างในสไลด์ 45 และ 46 แตะ field ที่ไม่ใช่ key ทีละตัว แล้วดูว่ามันขึ้นกับอะไร

Normalize ตารางคลินิกทันตกรรมทีละขั้นUNF → 1NF → 2NF → 3NF

คลินิก "ยิ้มสดใส" เก็บการนัดหมายไว้ใน spreadsheet ตารางเดียว (แบบฝึกหัด ex-database-design) งานคือแปลงเป็น 3NF ให้ได้ 6 ตาราง และทุกขั้นระบุ PK, FK และ dependency ที่ทำให้ต้องแยก

ตารางเดิมมี 17 field จัดกลุ่มได้ตามตารางปลายทาง สีของ field ในรูปคือตารางที่มันจะไปอยู่

  • APPOINTMENT ApptNo เลขที่นัด, ApptDate วันที่นัด
  • PATIENT PatID, PatName, PatAddr, PatPhone รหัส ชื่อ ที่อยู่ เบอร์โทรคนไข้
  • DENTIST DenID, DenName รหัสและชื่อทันตแพทย์
  • DEPARTMENT DeptID, DeptName, DeptFee รหัส ชื่อ ค่าธรรมเนียมตรวจของแผนก
  • PROCEDURE ProcID, ProcName, ProcCat, Duration, Price รหัส ชื่อ หมวด ระยะเวลามาตรฐาน ราคาต่อหน่วยของหัตถการ
  • TREATMENT Units จำนวนหน่วยที่รักษา (เป็นของคู่ นัด + หัตถการ)

เขียนเป็น [[notation|standard notation]]: ApptNo เป็น key ของตาราง ส่วนหัตถการเป็น [[repgroup]] ซ้ำได้หลายชุดต่อนัด จึงใส่ในวงเล็บปีกกา และ ProcID เป็น key ของชุดนั้น

UNF → 1NF: แตก repeating group

เปลี่ยนจาก [[unf]] เป็น [[nf1]] โดยแตกชุดหัตถการให้เป็นแถวละหนึ่งหัตถการ และขยาย key ให้รวม ProcID ตารางด้านล่างแสดงเฉพาะบางคอลัมน์เพื่อให้พอดีจอ field ที่เหลือ (วันที่ ที่อยู่ เบอร์โทร แผนก ชื่อและราคาหัตถการ) ตามไปอยู่ในแถวเดียวกันทั้งหมด

1NF → 3NF: ถามว่าแต่ละ field ขึ้นกับใคร

เลื่อนแถบทีละขั้น กรอบสีแดงคือกลุ่ม field ที่ขึ้นกับตัวกำหนดด้านบนผิดวิธี (ทำให้ไม่ผ่านรอบนั้น) กรอบสีเขียวคือขึ้นกับถูกวิธี แตะ field เพื่อดูว่ามันขึ้นกับอะไร

วาด ERD จากตาราง 3NFERD with cardinality

ทุก FK คือหนึ่งเส้นใน [[erd]]: ตารางที่เป็นเจ้าของ PK อยู่ฝั่ง 1 ตารางที่ถือ FK อยู่ฝั่ง many ใส่คำกริยากำกับ แล้วเติม [[cardinality]] ทั้งสองปลาย

  1. เขียนกล่อง entity ตามตาราง 3NF (ชื่อเอกพจน์)
  2. ไล่ FK ทีละตัว: ลากเส้นจากตารางที่ถือ PK ไปตารางที่ถือ FK
  3. ปลายฝั่ง PK ใส่ขีดสองขีด (one and only one) ปลายฝั่ง FK ใส่ตีนกา แล้วเลือกวงกลมหรือขีดตามกฎของธุรกิจว่าบังคับมีอย่างน้อยหนึ่งไหม
  4. ตั้งชื่อเส้นด้วยคำกริยาแล้วอ่านออกเสียงสองทิศ

แตะเส้นหรือกล่องในผังเพื่ออ่าน

เขียนคำตอบข้อสอบWritten answer template

คะแนนแบ่งตามขั้น เขียนให้ครบ 5 ส่วน: anomaly ของตารางเดิม, 1NF, 2NF, 3NF (แต่ละขั้นมี PK, FK และ dependency) แล้วปิดด้วย ERD พร้อม cardinality บรรทัดสีจางคือสิ่งที่ต้องทำในขั้นนั้น บรรทัดสีเข้มคือสิ่งที่เขียนจริง

ออกแบบตารางจากโจทย์เรื่องราวScenario → tables → ERD

โจทย์อีกแบบไม่ให้ตารางมา ให้แค่เรื่องเล่า วิธีคิดมี 6 ขั้นเสมอ: คำนามคือ [[entity]], รายละเอียดคือ field, เลือก [[pk]], หาความสัมพันธ์ (M:N ต้องมีตารางกลาง), วาง [[fk]] ที่ฝั่ง many และตัดค่าที่คำนวณได้ทิ้ง

ตัวอย่างแรกคือแบบฝึกหัด ABC ในสไลด์ (รายงานยอดขายตามสาขา รัฐ ประเทศ) อีก 3 เรื่องเป็นโจทย์ฝึกแบบเดียวกัน เลือกเรื่องแล้วเลื่อนดูทีละขั้น

ผลลัพธ์ที่ได้อยู่ใน 3NF ทันทีถ้าทำครบ 6 ขั้น เพราะแต่ละตารางเก็บเรื่องเดียว ข้อมูลของ entity อื่นอ้างผ่าน FK เท่านั้น ในข้อสอบให้เขียนแบบ standard notation แล้วตามด้วย ERD
